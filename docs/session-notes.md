## 1. v1 — 막차 카운트다운

### 요구사항
- 두 사람의 이름, 출발역, 막차 시각, 역까지 도보 시간(분)을 입력합니다.
- 각자 출발 시각 = 막차 − 도보 − 5분.
- 둘 중 먼저 출발해야 하는 사람 기준으로 큰 카운트다운을 보여줍니다. 30분 남으면 노랑, 10분 남으면 빨강입니다.
- 저장은 localStorage에만 합니다. 모바일 우선 PWA입니다.
- 자정을 넘기는 막차(예: 00:30)도 처리합니다.

### 핵심 설계
- **운행일 경계 04:00:** 04:00 이전 시각은 전날 운행일의 +24시간으로 봅니다. 그래서 23:50에 보면 00:30 막차가 40분 뒤로 계산됩니다.
- 시간 로직은 DOM 없는 순수 함수로 두고 테스트했습니다(11개).
- 서비스 워커로 오프라인에서도 열리게 했습니다.

### 배포 과정
- Node는 nvm으로 설치했고, Python은 필요 없어서 설치하지 않았습니다.
- git 저장소 `noeheat/lastrain`을 만들고 gh CLI를 설치했습니다.
- GitHub Pages는 직접 켜 주셨습니다(자동 설정이 권한 정책에 막혔기 때문).

## 2. v2 방향 정하기 — "현재 위치에서 막차 자동 계산"

### 요구
현재 위치(또는 직접 지정한 위치)에서 도착지까지 가는 경로의 막차 시각을 한 번에 계산합니다.

### API 탐색과 결론
| API | 검토 결과 |
|---|---|
| **TMAP 대중교통** | 출발 시각 지정과 운행 여부(`service`) 제공. 하지만 **자정 이후 운행을 표현하지 못함**: 00:00이 되면 전 노선이 운행종료로 나오고, 24시 이상 표기는 400 에러. 무료 10회/일. → **제외** |
| ODsay | 검토만 함 |
| 서울시 공공데이터 | 데이터가 오래됐고 서울 한정이라 사용하지 않기로 함 |
| **TAGO 지하철정보 (국토부)** | 전국 지하철 시간표. 자정 이후 시각과 종착역 포함. 무료 10,000회/일. → **막차 시각 소스로 채택** |
| **카카오 대중교통 길찾기** | 경로 구조(어느 노선, 어디서 환승, 정차역 목록)를 제공하고 시각 파라미터는 없음. → **경로 구조 소스로 채택** (카카오맵 서비스 활성화 필요) |

- 실제 검증 예시: 강남 → 홍대입구, 평일 막차 **00:21** (홍대입구행). 이후 테스트 기준값으로 씁니다.
- 실시간 정보가 아니라 계획 시간표라는 점, 시간표가 대체로 신뢰할 만하지만 임시 변경은 반영되지 않는다는 점도 확인했습니다.

### v2 범위 합의
- v2는 지하철만, v2.1은 서울 버스, v2.2는 그 외 지역 버스(추정)로 진행합니다.
- 스택: Next.js(App Router) + TypeScript strict + Tailwind + pnpm, Vercel 서울 리전(icn1).
- DB와 Supabase는 쓰지 않습니다. 입력 검증은 zod, 테스트는 vitest입니다.
- 출발지(현재 위치)는 두 사람이 공유하고, 도착지는 사람마다 따로 둡니다.
- v1의 수동 입력은 대체 수단으로 남겨 둡니다.

## 3. v2 진행 내역

### 1단계: Next.js 전환 (v1과 기능 동일)
- `time.js`를 `lib/time.ts`로 옮겼습니다(로직은 같고 타입만 추가).
- 화면은 React 컴포넌트 `LastTrainApp`, `SetupForm`, `Countdown`으로 나눴습니다.
- 입력 검증은 zod 스키마(`lib/schema.ts`)로 바꿨습니다. 클라이언트와 서버가 같이 씁니다.
- 테스트는 vitest로 옮겼습니다(11개 통과).
- 서비스 워커 캐시 정책: `/_next/static`은 캐시 우선, 페이지는 네트워크 우선, `/api`는 캐시하지 않습니다.
- `vercel.json`에 리전 icn1과 `framework: nextjs`를 지정했습니다.
- typecheck, test, build가 모두 통과했고, 브라우저에서 검증, 카운트다운, 수정 흐름을 확인했습니다.
- 확인하지 못한 것: 로컬 브라우저 패널에서는 서비스 워커를 등록할 수 없었습니다. HTTPS 배포 후 확인해야 합니다.

### 도착역 막차 판정 — 첫 시도 실패와 교훈
- **첫 시도:** 출발역과 도착역 시간표를 짝지어 "이 열차가 도착역까지 가는지" 판정하려 했습니다(`spike/tago-reach.js`).
- **실패한 이유:** TAGO 시간표에는 **열차 번호가 없습니다**. 배차가 3~5분이면 다른 열차와 짝지어지고, 9호선처럼 급행이 섞이면 소요시간 추정도 깨집니다. 2호선은 맞았지만 9호선 신논현→김포공항에서 틀렸습니다.
- **해결:** TAGO 역 ID의 번호가 노선 안에서 진행 순서대로 붙어 있는지 검증했습니다(`spike/tago-order.js`). 대부분 노선에서 일관됐습니다. 예외는 다음과 같습니다.
  - 2호선 순환과 지선
  - 1호선 (노선 ID가 둘이고 `P` 접두가 붙음)
  - 경의중앙선
  - 5호선 지선

### `lib/reach.ts` — 막차 판정 로직 (커밋 `21b7fbe`)
- 역 ID 번호를 비교해 방향과 "종착역이 도착역 너머에 있는지"를 판정합니다.
- 2호선 본선(201~243)은 순환으로 따로 계산합니다.
- 지선은 도착역 시간표에 같은 종착역 열차가 서는지로 한 번 더 확인합니다.
- **판정할 수 없는 열차는 "안 간다"로 봅니다.** 틀리더라도 더 이른 막차를 알려주는 쪽이 안전하기 때문입니다.
- 테스트는 `tests/reach.test.ts`에 있습니다.

### API 라우트 (커밋 `258c160`)
- `/api/stations?q=` : 역 이름 검색.
- `/api/last-train?origin=&dest=&daily=` : 도착역까지 가는 막차.
- TAGO 키는 서버에서만 씁니다. 역 목록과 시간표는 하루 동안 캐시합니다.
- 쿼리는 zod로 검증합니다(역 ID 형식 검사, 출발역과 도착역이 같으면 거부).
- 요일 코드(01 평일, 02 토, 03 일·공휴일)는 클라이언트가 운행일 기준으로 계산해 보냅니다.

### 역 선택 UI (작업 중, 커밋 전)
- `StationPicker`: 역을 검색해서 고릅니다.
- `TrainChoices`: 같은 노선이면 막차를 자동으로 채우고, 다른 열차도 고를 수 있습니다. 수정 화면에서 직접 고친 값은 덮어쓰지 않습니다.
- 환승 경로는 아직 계산하지 않습니다. 이 경우 "막차 시각을 직접 입력해 주세요"라는 안내를 보여줍니다.
- `Person`에 `origin`·`dest`(역 ID, 이름, 노선)를 선택 필드로 추가했습니다. 기존 저장값과 호환됩니다.

## 4. 키와 환경 변수
`.env.local`에만 저장하고 커밋하지 않습니다. 형식은 `.env.example`을 참고하세요.
- `TAGO_SERVICE_KEY`: 공공데이터포털 TAGO 지하철정보. 디코딩 키를 씁니다.
- `KAKAO_REST_API_KEY`: 카카오 디벨로퍼스 앱 "lastrain"의 REST 키. 카카오맵 활성화가 필요합니다.
- `TMAP_APP_KEY`: 스파이크에서만 썼고 앱에서는 쓰지 않습니다.
